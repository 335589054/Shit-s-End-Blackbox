# 01 · 需求规格说明书（SRS）

- 项目：史终黑盒（Shitsend Blackbox）
- 包名：`mai.solium.shitsendblackbox`
- 版本：v0.1（草稿，随实现同步修订）
- 平台：Android 8.0（API 26）及以上；主要验证 Android 12 / 16
- 运行时权限模型：**仅 Shizuku（shell, uid 2000）**，不使用 Root

---

## 1. 背景与目标

运营商与手机厂商预装的系统组件（`priv-app`）普遍具备以下特征：

- 默认获得全部权限，用户无法在设置中撤销；
- 无桌面图标、无用户可见界面，后台常驻；
- 静默上传通讯录、短信、应用列表、位置、甚至屏幕内容；
- 厂商拦截 `pm uninstall` 命令路径，普通卸载手段无效。

本项目提供一个**可审计、可回滚、无需 Root** 的本机工具，完成四类操作：

1. **清理**：识别疑似组件；卸载并以“同包名异签名空包”顶替，阻断 OTA 再生；保留原包备份以便恢复；无法卸载时降级为隔离。
2. **权限白名单**：用黑 / 灰 / 白三区管理应用，对网络、定位、录屏三类能力分别施加“禁止 / 仅前台 / 允许”策略。
3. **网络封锁**：按域名 / IP 选择性阻断上传通道；域名解析到 `127.0.0.1`，IP 直接丢包；支持手动添加与总开关。
4. **设置**：Shizuku 申请与管理、备份管理、日志导出。

### 1.1 非目标

- 不提供 Root 提权、不修改系统分区、不绕过设备所有者（Device Owner）策略。
- 不实现完整的防火墙 / TCP 代理；网络模块只做 **DNS 污染 + 定向 IP 丢包**。
- 不承诺覆盖所有厂商的私有权限模型；对无法生效的策略必须**如实提示**，不得静默失败。
- 不上传任何用户数据；应用本身不联网（除可选的订阅源更新外，默认关闭）。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 系统应用 | `ApplicationInfo.FLAG_SYSTEM` / `FLAG_UPDATED_SYSTEM_APP` 为真，或位于 `/system`、`/product`、`/vendor` 分区 |
| 顶替包（Stub） | 与目标同包名、`versionCode=25565`、使用本应用签名、无任何组件与权限的空 APK |
| 区域 | 应用所属的策略组：黑区 / 灰区 / 白区 |
| 灰区 | 仅当应用处于前台（或最近活跃）时允许相应能力 |
| 备份 | 删除前复制到应用私有目录的原 APK（含 split）及元数据 |
| 隔离 | 不删除包，仅强停、撤销权限、禁止后台联网/定位/录屏 |
| 策略应用 | 把某区域的规则落到系统（appops / netpolicy / pm / am）的动作 |

## 3. 用户与场景

### 3.1 目标用户

- 关注隐私、愿意承担一定系统风险的高级用户；
- 已安装 Shizuku（或愿意按引导启用无线调试）的 Android 用户；
- 需要审计预装组件的安全研究人员。

### 3.2 典型场景

1. 用户发现“系统安全组件”后台上传应用列表与截屏，扫描后将其**卸载并顶替**，重启后确认未被 OTA 恢复。
2. 用户误删了某个系统组件导致闹钟不响，进入备份页**恢复**原包。
3. 用户把某国产 App 放入灰区：锁屏后它无法联网、无法定位、无法录屏；回到前台后恢复正常。
4. 用户开启网络模块，屏蔽某统计 SDK 的 3 个域名与 2 个 IP，验证 App 不再上报。

## 4. 功能需求

### FR-1 清理模块

#### FR-1.1 扫描

- 点击“扫描”后列出候选应用，至少包含：
  - 包名、应用名、版本号、UID、是否系统应用、安装/更新时间、签名摘要、目标 SDK；
  - 已授予的敏感权限（通讯录、短信、通话记录、电话状态、精确定位、麦克风、相机、屏幕捕获、应用列表）；
  - 是否具备网络权限；
  - 风险分（0–100）与判定理由（可展开）。
- 支持筛选：全部 / 仅系统 / 仅第三方 / 已顶替 / 已隔离 / 高风险。
- 支持搜索包名。
- 扫描必须可在 10 秒内完成 300 个包（Android 12 模拟器基准），不得阻塞主线程。

#### FR-1.2 卸载并顶替

前置条件：Shizuku 已授权；目标包已备份成功。

流程：

1. 二次确认（高危包需输入包名后确认）；
2. **备份**：复制 base APK 与全部 split APK 到 `files/backups/<pkg>/`，记录元数据并校验 SHA-256；备份失败则中止；
3. **删除**：以 shell 身份执行 `app_process`，反射调用
   `IPackageManager.deletePackageAsUser(pkg, -1, observer, userId, DELETE_KEEP_DATA | DELETE_SYSTEM_APP)`；
4. **校验**：确认 `pm list packages` 中已无该包；
5. **顶替**：生成同包名、`versionCode=25565`、异签名、无组件、无权限的 Stub APK，`pm install --user 0` 安装；
6. **校验**：确认 Stub 已安装且版本号为 25565；
7. **失败回滚**：任一步失败，立即尝试从备份恢复原包，并把错误写入日志与界面。

验收：

- 删除成功后 `pm list packages` 不再包含目标；
- Stub 安装成功后 `dumpsys package <pkg>` 显示 `versionCode=25565`，签名摘要与原包不同；
- 设备重启、模拟 OTA 重装原包时，因签名冲突安装失败（即“阻断再生”生效）；
- 备份可完整恢复原包（签名、版本、split 均一致）。

#### FR-1.3 恢复

- 列出所有备份：包名、备份时间、大小、原版本、签名摘要、校验状态。
- 恢复前二次确认；恢复流程：
  1. 若当前存在 Stub，先卸载 Stub（`pm uninstall --user 0`，失败则 `deletePackageAsUser`）；
  2. `pm install-multiple -r --user 0` 安装 base + splits；
  3. 校验签名 / 版本；
  4. 恢复原来的启用状态与 appops；
  5. 标记备份为“已恢复”，保留副本直至用户手动删除。
- 支持导出备份到用户选择的目录（SAF）。

#### FR-1.4 隔离

适用于无法卸载或用户不想删除的情况：

- 强制停止；
- 撤销运行时敏感权限（`pm revoke`，尽力而为）；
- appops：定位 `ignore`、录屏 `deny`、后台运行 `ignore`；
- 网络：加入 `restrict-background-blacklist`；尝试 `pm disable-user`（失败不阻断）；
- 记录隔离状态；提供“解除隔离”，按原状态恢复。

#### FR-1.5 守护

- 开机、应用被替换/重装、定时任务触发时，复查已顶替包是否仍为 Stub；
- 若系统恢复了原包（签名变化 / 版本变化），提示用户并可一键重新顶替；
- 守护不得在未授权时静默执行删除。

### FR-2 权限白名单

#### FR-2.1 三区模型

| 区域 | 网络 | 定位 | 录屏 | 其它 |
|---|---|---|---|---|
| 黑区 | 禁止 | 禁止 | 禁止 | 强停 + 禁止后台；可选整体禁用 |
| 灰区 | 仅前台 | 仅前台（`MODE_FOREGROUND`） | 仅前台 | 后台联网/定位受限 |
| 白区 | 允许 | 允许（可开“反卫星直读”） | 允许 | 不限制 |

- 每个应用同一时刻只能属于一个区域；默认全部为白区。
- 提供“一键把高危应用移入黑区”。

#### FR-2.2 3×3 表格

- 首页展示 3 行（黑/灰/白）× 3 列（网络/定位/录屏）的矩阵；
- 每个单元格显示：该区域应用数、当前策略短语、生效状态（已生效/部分失败/未授权）；
- 点击行标题或单元格 → 进入该区域的应用列表；
- 列表支持多选，批量移动到其它区域；
- 每次变更后点“应用策略”统一落盘；落盘结果逐项显示成功/失败原因。

#### FR-2.3 反卫星直读（白区定位增强）

- 白区默认允许 `COARSE_LOCATION` 与 `FINE_LOCATION`；
- 开启“反卫星直读”后，对白区应用执行：
  - `FINE_LOCATION` → `ignore`（或 `foreground`，视配置）；
  - `COARSE_LOCATION` → `allow`；
  - 目的：保留网络/基站定位，阻断需要 `ACCESS_FINE_LOCATION` 的 GNSS 原始观测（`GnssMeasurements`）。
- 界面必须说明：该模式会降低定位精度，且无法阻止已获得系统级定位服务的特权应用。

### FR-3 网络封锁

#### FR-3.1 总开关

- 首次开启需系统 VPN 授权；
- 关闭后立即撤销 TUN、恢复 DNS；
- 前台常驻通知显示拦截计数与开关。

#### FR-3.2 域名规则

- 内置种子黑名单（见 `docs/05-黑名单数据规范.md`）；
- 支持按域名后缀匹配（`example.com` 匹配 `a.example.com`）；
- 命中域名返回 `A=127.0.0.1`、`AAAA=::1`，TTL 60；
- 未命中域名转发到上游 DNS（默认 `223.5.5.5`，可改）；
- 支持单条启用/禁用、整组启用/禁用；
- 支持手动添加域名。

#### FR-3.3 IP 规则

- 支持单 IP 与 CIDR（`1.2.3.4`、`1.2.3.0/24`）；
- 命中流量在 TUN 内直接丢弃（不转发、不回 RST）；
- 支持手动添加/删除；
- 展示每条规则的命中计数（尽力而为，按包计数）。

#### FR-3.4 绕过与限制

- 明确提示：DoH / DoT / 硬编码 IP / 代理可绕过 DNS 污染；IP 丢包仅覆盖进入 TUN 的地址。
- 不代理 TCP/UDP 业务流量，避免实现完整协议栈带来的耗电与兼容问题。

### FR-4 设置

- Shizuku：
  - 状态：未安装 / 未运行 / 未授权 / 已授权；
  - 申请权限、打开 Shizuku、无线调试配对指引；
  - 显示 Shizuku 版本、UID、权限到期策略；
  - 一键复制启动命令（用于 adb / 无线调试）。
- 备份：列表、校验、导出、删除。
- 日志：最近 500 条操作日志，支持导出文本；敏感字段脱敏。
- 关于：版本、开源许可、免责声明。
- 危险区：清空所有策略、清空备份（二次确认）。

## 5. 非功能需求

| 编号 | 要求 |
|---|---|
| NFR-1 | 运行时零 Root；所有特权操作经 Shizuku（uid 2000）完成 |
| NFR-2 | 无网络权限滥用：应用自身不发起业务网络请求；VPN 仅本机 |
| NFR-3 | 所有删除/恢复操作必须可回滚；备份校验失败禁止删除 |
| NFR-4 | 关键系统包（`android`、`systemui`、`phone`、`settings`、`packageinstaller` 等）默认禁止操作，需显式解锁并输入包名 |
| NFR-5 | 崩溃率：主流程不得因单个包解析失败而整体失败；单包异常隔离 |
| NFR-6 | 兼容 Android 8–16；Shizuku 13.x |
| NFR-7 | 界面全中文；深色/浅色跟随系统 |
| NFR-8 | 安装包 < 5 MB（不含可选 apksig 依赖时 < 8 MB） |
| NFR-9 | 所有 shell 命令必须带超时（默认 15s），避免卡死 |
| NFR-10 | 日志不得记录完整手机号、IMSI、IMEI、通讯录内容 |

## 6. 验收标准（摘要）

1. 在 Android 12 AOSP 模拟器（root 仅用于注入测试包）上：
   - 成功扫描出注入的 3 个“泄密系统组件”与 2 个第三方样本；
   - 对 `com.mobiletools.systemhelper` 样本完成备份 → 删除 → 顶替 → 重启 → 验证 Stub 仍在；
   - 删除后立刻恢复，签名与版本与原包一致。
2. 3×3 矩阵：
   - 黑区应用锁屏后无网络、无定位、无法录屏；
   - 灰区应用切后台 30 秒后无网络，回前台恢复；
   - 白区应用正常联网、定位、录屏。
3. 网络模块：
   - 命中域名的 DNS 查询返回 127.0.0.1；
   - 未命中域名正常解析；
   - 命中 IP 的 TCP 连接超时，未命中 IP 正常；
   - 关闭 VPN 后一切恢复。
4. 无 Root 环境（模拟器 `adb unroot` 后仅 Shizuku）下，上述功能仍可用。

## 7. 风险与合规（详见 03）

- 删除系统组件可能导致功能缺失、OTA 失败、无法开机；
- 顶替包会阻止官方更新，可能触发厂商完整性校验；
- 用户必须确认对设备有管理权；本项目不提供规避设备管理策略的能力。
