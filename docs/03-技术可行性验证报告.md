# 03 技术可行性验证报告

> 版本：v0.1（2026-11-09）
> 验证环境：Windows 11 + Android Emulator 31.3.14 + AOSP Android 12 (API 31, userdebug, x86_64)
> 验证方式：`adb root` 注入测试 APK / priv-app，Shizuku 13.6.0 root 模式起服务，shell uid 2000 执行命令。

## 1. 验证目标

在写业务代码之前，先回答四个决定架构的问题：

| # | 问题 | 影响 |
|---|------|------|
| Q1 | `app_process` + 反射 `IPackageManager.deletePackageAsUser` 能否从 shell(uid 2000) 调用并真正删包？ | 卸载模块的可行性 |
| Q2 | 删除后能否安装 **同包名、不同签名、versionCode 25565** 的空包完成“顶替”？ | 防 OTA 再生方案是否成立 |
| Q3 | 删除后能否恢复原系统组件？ | 误删兜底 |
| Q4 | 权限/网络模块依赖的 `cmd appops`、`cmd netpolicy`、`pm suspend` 是否可用？ | 隔离与三区策略的实现路径 |

## 2. 结论速览

| 项 | 结果 | 说明 |
|----|------|------|
| Q1 删除调用 | ✅ 通过 | uid 2000 可调用；`pm path` 1s 内消失；无 MIUI 式命令拦截 |
| Q2 异签名顶替 | ❌ AOSP 12 失败 | PMS 保留 tombstone（禁用系统包记录）与原证书，安装报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` |
| Q3 恢复 | ✅ 通过 | `pm install-existing <pkg>` 可恢复；系统分区 APK 未动时最可靠 |
| Q4 权限/网络原语 | ✅ 基本通过 | `PROJECT_MEDIA`、定位 appops、`netpolicy`、`pm suspend` 均可用；**无 INTERNET appop** |

**核心结论**：卸载与恢复链路在 AOSP 12 上成立；“异签名顶替”受 PMS tombstone 限制，在本验证环境无法完成，需要在 Android 17 / OS4 等新版本上复验，或改用“同签名高版本空包”作为备选路线。应用必须实现**顶替失败自动降级为隔离**，不能把顶替当作唯一路径。

## 3. 详细验证记录

### 3.1 测试物料

| 物料 | 包名 | versionCode | 签名 | 说明 |
|------|------|-------------|------|------|
| leaky.apk | `com.test.leaky` | 1 | debug.keystore（RSA2048, CN=BlackBox Debug） | 模拟被注入的“泄露隐私系统应用”，装入 `/system/priv-app/Leaky/Leaky.apk` |
| stub.apk | `com.test.leaky` | 25565 | ks2.p12（CN=BlackBox Stub） | 同包名异签名空包，`hasCode=false`、`enabled=false`、无组件 |
| uninstaller.jar | — | — | — | `com.dsh.sysguard.PackageUninstaller`，dex 放入 jar，`app_process` 执行 |

构建链：`aapt2 link` → `zipalign -p -f 4` → `apksigner sign`；Java 侧 `javac -source 8 -target 8 -bootclasspath android.jar` → `d8 --min-api 26` → `jar cf uninstaller.jar classes.dex`。

### 3.2 Q1：反射删除

调用方式：

```sh
CLASSPATH=/data/local/tmp/uninstaller.jar app_process /system/bin \
  com.dsh.sysguard.PackageUninstaller com.test.leaky 0 5
```

- 必须 uid 2000（`adb root` 后需 `su 2000 sh -c "..."`，或 `adb unroot`）。
- flags = `DELETE_KEEP_DATA(1) | DELETE_SYSTEM_APP(4)` = 5。
- 反射签名：`deletePackageAsUser(String packageName, int versionCode, IPackageDeleteObserver observer, int userId, int flags)`，versionCode 传 -1。

结果：

- 普通应用、系统 priv-app 均删除成功，`pm path` 立即为空。
- **但** `pm list packages -u` 仍能列出该包，`/data/system/packages.xml`（ABX 二进制）保留原包记录及证书 DER。

### 3.3 Q2：异签名顶替（失败）

| 尝试 | 结果 |
|------|------|
| flags=5 删除后装 stub | `INSTALL_FAILED_UPDATE_INCOMPATIBLE: signatures do not match previously installed version` |
| flags=4（仅 DELETE_SYSTEM_APP） | 同上 |
| flags=6（DELETE_ALL_USERS\|DELETE_SYSTEM_APP） | 同上 |
| 重启后再装 | 同上（tombstone 持久化） |
| `adb remount` 后删除 `/system/priv-app/Leaky/Leaky.apk` 再装 | 同上（tombstone 仍在 packages.xml） |

原因分析：AOSP 的 `PackageManagerService` 对“已删除的系统应用”保留 *disabled system package* 记录（用于 `pm install-existing` 与 OTA 恢复），该记录携带原始签名；安装校验会拿新 APK 签名与之比对，签名不同即拒绝。

对用户所述“OS4 / Android 17 放行”的判断：较新版本 PMS 在 `DELETE_SYSTEM_APP` 时可能直接清掉该记录，从而使异签名安装可行；本机 AOSP 12 无法证明，也不能证伪。**该路径必须做运行时探测，不能硬编码假设。**

### 3.4 Q3：恢复

- `pm install-existing com.test.leaky` → `installed for user 0`，组件恢复，数据保留（因删除时用了 KEEP_DATA）。
- 若系统分区 APK 被人为删除，则 `install-existing` 失败，需要 `adb push` 回 `/system/priv-app`（需 root + remount），这不是普通用户路径。因此应用**不得**主动删除系统分区文件，只做 PMS 层删除。

### 3.5 Q4：权限与网络原语

| 命令 | 结果 |
|------|------|
| `cmd appops set <pkg> PROJECT_MEDIA deny` | ✅ 成功（录屏控制可用） |
| `cmd appops set <pkg> FINE_LOCATION ignore` / `COARSE_LOCATION ignore` | ✅ 成功 |
| `cmd appops set <pkg> FINE_LOCATION foreground` | ✅ 成功（灰区“仅前台”语义） |
| `cmd appops set <pkg> INTERNET deny` | ❌ `Error: Unknown operation string: INTERNET`，rc=255 |
| `cmd netpolicy add restrict-background-blacklist <uid>` | ✅ 存在（仅后台限制，非完全断网） |
| `pm suspend --user 0 <pkg>` / `pm unsuspend` | ✅ 成功（可作强隔离） |
| `pm disable-user --user 0 <pkg>` | ✅ 成功 |

**网络完全阻断**没有现成 appop，只能靠以下组合：
1. **本地 VPN**：把该 uid 的流量路由进黑洞（本应用自己实现 VpnService，仅拦该 uid 的 IP 包）；
2. `pm suspend`（冻结进程，联网随之停止）；
3. 灰区：`netpolicy restrict-background-blacklist` + 前台放行。

这也决定了网络模块采用 VpnService 而不是改 iptables（无 root）。

### 3.6 Shizuku 可行性

- Shizuku 13.6.0 以 root 起服务：`rikka.shizuku.server.ShizukuService`（`moe.shizuku.server.*` 是错误类名）。
- 应用侧 `Shizuku.newProcess` 在 13.1.5 API jar 中不存在，需：
  `IShizukuService.Stub.asInterface(new ShizukuBinderWrapper(Shizuku.getBinder())).newProcess(new String[]{"sh","-c",cmd}, null, null)`。
- `ShizukuProvider` 需在 manifest 注册，authority `${applicationId}.shizuku`，并声明 `moe.shizuku.manager.permission.API_V23`。
- 结论：Shizuku 作为唯一提权通道可行；所有 shell 操作走同一条 `newProcess` 通道即可。

### 3.7 环境限制记录

- Emulator 37.2.13 在本机因 netsimd 启动被拒（`os error 5`）无法引导，已降级到 31.3.14（pre-netsim）。
- `adb` 需要自定义 `TMP`，否则报 `cannot open ...\Temp\adb.log: Permission denied`。
- `adb install` 在 API 31 默认走 Incremental Install，测试时出现“删除后包又出现”的干扰；测试脚本统一加 `--no-incremental`，应用内 `pm install` 不受影响。

## 4. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| 异签名顶替在目标机型被 PMS 拒绝 | 高 | 安装前探测；失败即降级隔离；UI 明确提示“本机不支持顶替，已改为隔离” |
| 厂商在 `app_process` 路径加 SELinux 限制 | 中 | 捕获 stderr/退出码，映射为可读错误；提供“诊断”页 |
| `pm install-existing` 在部分 ROM 不可用 | 中 | 保留 APK 备份 + `pm install -r` 兜底（同签名可覆盖） |
| VPN 与系统 VPN/代理冲突 | 中 | 检测已有 VPN，提示用户；只接管 DNS 与黑名单 IP，减少影响面 |
| 误删关键组件导致无法开机 | 高 | 内置关键包黑名单（systemui/settings/phone/telephony provider 等），强制二次确认 + 备份校验 |
| 应用被杀后策略失效 | 中 | 前台服务 + 开机广播 + 定时校验（JobScheduler） |

## 5. 待复验项（真机 / Android 17）

1. `DELETE_SYSTEM_APP` 后 tombstone 是否消失、异签名 stub 能否安装。
2. `pm install-existing` 在 MIUI/HyperOS 上的行为。
3. `PROJECT_MEDIA deny` 对 `MediaProjection` 的实际拦截效果（含系统录屏）。
4. VPN 内 DNS 污染对 DoH/DoT 的覆盖程度（预期无法覆盖，需在文档中声明）。
5. Shizuku 非 root（adb 启动）模式下 `newProcess` 的权限边界。

## 6. 对实现的约束（已落入设计）

- 所有特权操作必须可失败、可回滚、可解释；禁止“假定成功”。
- 顶替流程：备份 → 删除 → 试装 stub → 校验 `pm path` 与 versionCode → 失败则 `install-existing` 回滚 → 降级隔离。
- 不修改 `/system` 分区；恢复只依赖 PMS 记录与备份 APK。
- 网络阻断用 VpnService + 每应用 uid 规则，不依赖 root/iptables。
- 所有危险操作前做备份完整性校验（文件存在、大小>0、可解析包名）。
